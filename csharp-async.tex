\section{Asynchronous Computing in C\#}

\showtitlepage{Asynchronous Computing in C\#}

\begin{frame}{Why Asynchrony at All?}
  A game must finish a frame before the display asks for the next one. How long
  that is depends on the target: roughly 16 ms on a 60\,Hz monitor, 11 ms on a
  VR headset at 90\,Hz, 7 ms at 144\,Hz. Whatever the number, it is a budget,
  and everything your code does is spent from it, on one thread. Read a file,
  wait for a web request, parse a large graph --- and the frame is gone,
  together with the next hundred.
  \vspace{1ex}

  \begin{itemize}
    \item \emph{Asynchronous} means: this operation may finish later, and the
      caller need not stand still meanwhile.
    \item \emph{Parallel} means: two things happen at the same instant, on two
      cores.
    \item The two are independent. Most asynchrony in Unity is
      \emph{single-threaded}: the work is chopped into pieces spread over
      frames, and no second thread is involved.
  \end{itemize}
  \vspace{2ex}

  \hint{Unity's API is not thread-safe and may only be touched from the main
  thread. That single rule explains most of the design decisions in this
  lecture.}
\end{frame}

\begin{frame}{Three Mechanisms, One Problem}
  \begin{center}
    \footnotesize
    \begin{tabular}{llll}
      \hline
      & \textbf{Coroutine} & \textbf{Task} & \textbf{UniTask}\\
      \hline
      Written as        & \texttt{IEnumerator}  & \texttt{async Task} & \texttt{async UniTask}\\
      Driven by         & the player loop       & the thread pool     & the player loop\\
      Returns a value   & no                    & yes                 & yes\\
      Propagates errors & no                    & yes                 & yes\\
      Allocates         & yes                   & yes                 & almost never\\
      Needs play mode   & yes                   & no                  & no\\
      Used in SEE       & occasionally          & not yet             & very often\\
      \hline
    \end{tabular}
  \end{center}
  \vspace{2ex}

  All three answer the same question --- \emph{how do I wait without
  blocking?} --- and SEE has settled on the third. The other two are covered
  because you will meet them in Unity's documentation, in tutorials, and in
  the older corners of any code base.
\end{frame}

\begin{frame}[fragile]{Coroutines: A Method That Can Pause}
  \framelabel{slide:coroutine}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/Avatars/AvatarAdapter.cs
public IEnumerator StartXRCoroutine()
{
  StartCoroutine(ManualXRControl.StartXRCoroutine());

  // Wait until XR is initialized.
  while (!ManualXRControl.IsInitialized())
  {
    yield return null;       // continue in the next frame
  }
  Debug.Log("XR is initialized.\n");
  // ... now instantiate the VR prefabs ...
}
  \end{lstlisting}
  \vspace{1ex}

  A coroutine is started with \texttt{StartCoroutine(\ldots)} on a
  \texttt{MonoBehaviour}. Unity then calls it back once per frame, and each
  \texttt{yield return} decides when the next call happens.
\end{frame}

\begin{frame}[fragile]{What \texttt{yield return} Really Does}
  The compiler turns the method body into a class implementing
  \texttt{IEnumerator}: a state machine whose \texttt{MoveNext} runs up to the
  next \texttt{yield} and remembers where it stopped.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
yield return null;                        // next frame
yield return new WaitForSeconds(0.5f);    // after 0.5 s of game time
yield return new WaitForEndOfFrame();     // after rendering this frame
yield return new WaitUntil(() => ready);  // until ready becomes true
yield return SomeOtherCoroutine();        // until that one finishes
yield break;                              // stop here
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item There is no magic and no thread: Unity simply calls
      \texttt{MoveNext} on your enumerator once per frame.
    \item \texttt{IEnumerator} is the same interface \texttt{foreach} uses. A
      coroutine is a sequence whose elements happen to be
      \emph{wait instructions}.
    \item Waiting is polling, not an event: \texttt{WaitUntil} evaluates its
      predicate once per frame, so an expensive predicate costs you every
      frame until it turns true.
  \end{itemize}
\end{frame}

\begin{frame}{Where Coroutines Fall Short}
  \begin{itemize}
    \item \textbf{No result.} \texttt{IEnumerator} cannot return a value. You
      write the result into a field and hope the caller reads it at the right
      time.
    \item \textbf{No exceptions.} A coroutine cannot be wrapped in
      \texttt{try/catch} by its caller, and it may not \texttt{yield} inside a
      \texttt{catch} block at all.
    \item \textbf{Bound to a component.} It needs a \texttt{MonoBehaviour} to
      run on, and it dies silently when that object is destroyed.
    \item \textbf{Play mode only.} \texttt{StartCoroutine} does nothing in the
      Editor, which puts every coroutine beyond the reach of an edit-mode test.
  \end{itemize}
  \vspace{2ex}

  \hint{A subtle one: deactivating the \emph{game object} stops its
  coroutines, but merely setting \texttt{enabled = false} on the component
  does not. The coroutine keeps running on a component you believe to be
  switched off.}
\end{frame}

\begin{exerciseframe}{Coroutine, Async, or Neither?}
  For each task, decide whether it wants a coroutine, an \texttt{async} method,
  or no asynchrony at all --- and say why in one sentence.
  \vspace{1ex}

  \begin{enumerate}
    \item Fade a node's color from red to green over two seconds.
    \item Read a 40\,MB GXL file from disk and build a graph from it.
    \item Compute the median of a list of floats.
    \item Download metrics from the Axivion dashboard over HTTP.
    \item Wait until the user has closed a dialog, then continue an action.
  \end{enumerate}
  \vspace{1ex}

  Which of them could be tested in an edit-mode test?
\end{exerciseframe}

\begin{solutionframe}{Coroutine, Async, or Neither?}
  \begin{enumerate}
    \item \textbf{Either.} It is per-frame animation, the home ground of
      coroutines --- though SEE would use DOTween or \texttt{UniTask.Yield}.
    \item \textbf{Async.} It returns a value and may fail; both are awkward in
      a coroutine. SEE parses it on a background thread.
    \item \textbf{Neither.} It is a pure computation that finishes in
      microseconds. Asynchrony would only add overhead.
    \item \textbf{Async.} Waiting for a server is the original use case, and
      the answer is a value.
    \item \textbf{Either}, and in SEE async: the dialog's result is a value,
      and \texttt{await} keeps the action's code in one readable piece.
  \end{enumerate}
  \vspace{1ex}

  \hint{Only the async ones, 2 to 5, can be tested in edit mode --- and only
  because they do not depend on the player loop. Anything built on
  \texttt{StartCoroutine} forces the test into play mode.}
\end{solutionframe}

\begin{frame}[fragile]{\texttt{async} and \texttt{await}}
  \framelabel{slide:asyncawait}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask<Graph> LoadAsync(DataPath path)
{
  Graph graph = await GraphReader.LoadAsync(path);  // suspends here
  Debug.Log($"Loaded {graph.NodeCount} nodes.\n");  // resumes here
  return graph;
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{async} is a promise about the method's \emph{body}: it may
      contain \texttt{await}. It changes nothing about how the method is
      called.
    \item \texttt{await} splits the method in two. Everything after it becomes
      a \emph{continuation} that runs once the awaited operation completes.
    \item The return type is the contract: \texttt{UniTask<T>} or
      \texttt{Task<T>} for a result, \texttt{UniTask} or \texttt{Task} for
      none.
  \end{itemize}
  \vspace{1ex}

  \hint{By convention an asynchronous method's name ends in \texttt{Async}.
  SEE follows this: \texttt{ProvideAsync}, \texttt{LoadAsync},
  \texttt{DeleteTableAsync}.}
\end{frame}

\begin{frame}[fragile]{What \texttt{await E} Does, Exactly}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// await GraphReader.LoadAsync(path), roughly as the compiler rewrites it
UniTask<Graph>.Awaiter awaiter = GraphReader.LoadAsync(path).GetAwaiter();
if (!awaiter.IsCompleted)                 // E has run; not finished yet?
{
  awaiter.UnsafeOnCompleted(MoveNext);    // register the rest of the body
  return;                                 // and hand control to the caller
}
Graph graph = awaiter.GetResult();        // the value, or a rethrow
  \end{lstlisting}
  \vspace{0.5ex}

  \begin{itemize}
    \item \textbf{The operand runs first.} \texttt{E} is evaluated before
      anything is registered: the call starts the work, never the
      \texttt{await}.
    \item \textbf{A finished operation costs nothing.} If \texttt{IsCompleted}
      is true, nothing is registered and no frame is lost.
    \item \textbf{Otherwise the rest of the method becomes the continuation},
      control returns to the caller, and the resumed method re-enters at
      \texttt{GetResult()}.
    \item \textbf{The method's own \texttt{return} is generated, too:} your
      \texttt{return graph;} becomes \texttt{builder.SetResult(graph)}, and the
      stub ends in \texttt{return builder.Task;} --- a plain
      \texttt{async UniTask} needs none, like \texttt{void}.
  \end{itemize}
\end{frame}

\begin{frame}{\texttt{await} Is Not a Thread}
  \framelabel{slide:notathread}
  The single most common misconception: \texttt{await} does not start a
  thread, and an \texttt{async} method does not run in the background.
  \vspace{2ex}

  \begin{itemize}
    \item Like a coroutine, an \texttt{async} method is compiled into a state
      machine. \texttt{await} means: register a continuation, return to the
      caller now, and resume later.
    \item \emph{Where} it resumes is decided by the awaited thing. In Unity,
      an awaited \texttt{Task} resumes on the main thread, because Unity
      installs a synchronization context that marshals it back.
    \item If you \texttt{await} something that never completes, nothing
      happens --- forever, and silently. No deadlock, no error.
  \end{itemize}
  \vspace{2ex}

  \hint{Concurrency without parallelism is the normal case here. Use
  \texttt{await} to stop \emph{waiting} on the main thread; use a thread pool
  to stop \emph{computing} on it. They solve different problems.}
\end{frame}


\begin{frame}[fragile]{\texttt{async void} Is a Trap}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
async void Load()             // nobody can await this
{
  throw new IOException();    // ... and nobody can catch it
}

try { Load(); }               // this catch never fires:
catch (IOException) { ... }   // Load returned before throwing
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item An \texttt{async void} method returns to its caller at the first
      \texttt{await}. There is no handle left to await, so the caller cannot
      know when it ends or whether it failed.
    \item Its exceptions do not travel to the caller. They surface as
      unhandled exceptions somewhere else entirely, or vanish.
    \item Use \texttt{async UniTask} instead. Where you genuinely want to
      start something and not wait, say so explicitly with
      \texttt{UniTaskVoid} and \texttt{Forget()} --- \emph{I know that nobody
      waits for this} (\slideref{slide:forget}).
  \end{itemize}
\end{frame}

  This compiles, runs, prints nothing, and reports no error. Explain what
  happens and repair the signature.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private Graph graph;

private async void LoadGraph(DataPath path)
{
  graph = await GraphReader.LoadAsync(path);
}

\end{exerciseframe}

\begin{solutionframe}{Why Is the Graph Never There?}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask LoadGraphAsync(DataPath path)
{
  graph = await GraphReader.LoadAsync(path);
}

private async UniTaskVoid Start()
{
  await LoadGraphAsync(gxlPath);
  Debug.Log($"{graph.NodeCount} nodes\n");   // now it is there
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{LoadGraph} returns at its \texttt{await}, long before the
      file is read. \texttt{Start} then reads a field that is still
      \texttt{null}.
    \item \texttt{async void} gave the caller nothing to wait for.
      \texttt{async UniTask} does, and \texttt{await} restores the order the
      code appears to have.
  \end{itemize}
  \vspace{1ex}

  \hint{The \texttt{NullReferenceException} is the lucky outcome. Had the
  graph been loaded a moment earlier, the bug would surface once a month on a
  slower machine.}
\end{solutionframe}

\begin{frame}{Why Cancel at All?}
  An operation worth starting a second ago may be pointless now: the user
  closes the city, reloads it from another GXL file, or leaves play mode ---
  while load, layout and request keep running for a result nobody waits for.
  \vspace{0.5ex}

  \begin{itemize}
    \item \textbf{Nothing else can stop it.} An \texttt{async} method is not a
      thread; there is no \texttt{Abort}. Either the operation ends itself, or
      it runs to its end.
    \item \textbf{A late result can do damage.} A load finishing after its city
      is gone writes into destroyed objects, or replaces the graph the user is
      looking at now.
    \item \textbf{Some operations never end.} A server that does not answer
      leaves your \texttt{await} pending forever, and silently
      (\slideref{slide:notathread}). A deadline turns that into a failure you
      can report, which is what \texttt{AsyncUtils.RunWithTimeoutAsync} does
      for SEE's dashboard and LSP requests.
  \end{itemize}
  \vspace{0.2ex}

  \hint{The one who cancels may be a clock: \texttt{CancellationTokenSource.CancelAfter(\ldots)}
  gives every animation phase of \texttt{TransitionRenderer} 15 seconds, after
  which its token is canceled like any other.}
\end{frame}

\begin{frame}[fragile]{Cancellation Is Cooperative}
  Nothing can abort a running method from outside. Cancellation is a
  \emph{request} that the operation itself has to honor.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
CancellationTokenSource source = new();   // the owner cancels
CancellationToken token = source.Token;   // the operation observes

// Somewhere in the operation, regularly:
token.ThrowIfCancellationRequested();     // throws OperationCanceledException

// Or, where throwing is inconvenient:
if (token.IsCancellationRequested) { return; }

source.Cancel();                          // from the other side
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item The \emph{source} is the switch and belongs to whoever starts the
      work; the \emph{token} is the wire and is passed down to everything the
      work calls.
    \item A token you never check is decoration. A token you never pass on
      cancels only the top of the call chain.
  \end{itemize}
\end{frame}

token.ThrowIfCancellationRequested();            // at every XML node

// Assets/SEE/Game/City/SEECity.cs -- on every reload, because a canceled
// source stays canceled:
cancellationTokenSource.Cancel();                // stop the old load
cancellationTokenSource = new CancellationTokenSource();
  \end{lstlisting}
  \vspace{0.5ex}

  \hint{The default of that parameter is \texttt{CancellationToken.None} --- a
  token that can never be canceled. Convenient in tests, a silent loss of
  cancellation everywhere else.}
\end{frame}

\begin{frame}[fragile]{Canceled: Throw or Return?}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// The normal case: the caller must not mistake this for a finished job.
token.ThrowIfCancellationRequested();

// The same thing, written out. Naming the token matters: without it,
// nobody can tell whose cancellation this was.
if (token.IsCancellationRequested)
{
  throw new OperationCanceledException(token);
}

// Returning is right only where the contract promises partial work:
if (token.IsCancellationRequested) { return builtSoFar; }
  \end{lstlisting}
  \vspace{0.5ex}

  \begin{itemize}
    \item \textbf{Throw by default.} \texttt{UniTask} and \texttt{Task} record
      an \texttt{OperationCanceledException} as \emph{canceled}, not as
      failed, and \texttt{await} rethrows it for the caller to see.
    \item \textbf{Return only where nobody is misled}, as in a
      \texttt{UniTaskVoid} nobody awaits (\slideref{slide:forget}). A silent
      \texttt{return} that looks like success is how a half-loaded graph
      reaches the screen.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{Where to Check, What to Clean Up}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
GameObject spinner = ShowSpinner();
try
{
  foreach (Node node in graph.Nodes())   // once per node, not per byte
  {
    token.ThrowIfCancellationRequested();
    await FetchAsync(node.ID, token);    // handed on: no check needed
  }                                      // around the await itself
}
finally
{
  Destroyer.Destroy(spinner);            // runs when canceled, too
  await SaveDraftAsync(CancellationToken.None);   // a canceled token
}                                                 // would cancel this
  \end{lstlisting}

  \begin{itemize}
    \item \textbf{Check as often as the user would notice}: once per unit of
      work --- a node, an XML element, a file. Once at the start is decoration,
      once per byte is waste.
    \item \textbf{Let \texttt{finally} do the cleaning}: the exception travels
      through it, so the spinner goes either way, and so does the switch back
      to the main thread (\slideref{slide:mainthread}).
    \item \textbf{Last wishes need a live token}, never the one that was just
      canceled.
  \end{itemize}
\end{frame}

\begin{exerciseframe}{Make It Cancelable}
  This runs to the end even after the user has closed the city. Add
  cooperative cancellation, and explain who owns the source.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask AddMetricsAsync(Graph graph)
{
  foreach (Node node in graph.Nodes())
  {
    Metric metric = await dashboard.FetchAsync(node.ID);
    node.SetFloat("Metric.Complexity", metric.Value);
  }
}
  \end{lstlisting}
\end{exerciseframe}

\begin{solutionframe}{Make It Cancelable}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask AddMetricsAsync(Graph graph, CancellationToken token)
{
  foreach (Node node in graph.Nodes())
  {
    token.ThrowIfCancellationRequested();          // between iterations
    Metric metric = await dashboard.FetchAsync(node.ID, token);
    node.SetFloat("Metric.Complexity", metric.Value);
  }
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item Two changes, both necessary: check the token in the loop, and pass
      it to everything awaited inside. Checking alone still waits out the
      current request.
    \item The \emph{source} belongs to the city, which cancels it when the
      graph is reset. The method only ever sees the token.
  \end{itemize}
  \vspace{1ex}

  \hint{Do not catch \texttt{OperationCanceledException} to log an error.
  Cancellation is not a failure; it is the answer you asked for.}
\end{solutionframe}

\begin{exerciseframe}{Give It a Deadline}
  The dashboard sometimes does not answer at all, and the city then waits for
  ever. Give the loop a deadline of five seconds --- without taking the
  caller's own cancellation away.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask AddMetricsAsync(Graph graph, CancellationToken token)
{
  foreach (Node node in graph.Nodes())
  {
    token.ThrowIfCancellationRequested();
    Metric metric = await dashboard.FetchAsync(node.ID, token);
    node.SetFloat("Metric.Complexity", metric.Value);
  }
}
  \end{lstlisting}
\end{exerciseframe}

\begin{solutionframe}{Give It a Deadline}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask AddMetricsAsync(Graph graph, CancellationToken token)
{
  using CancellationTokenSource deadline           // canceled by either
      = CancellationTokenSource.CreateLinkedTokenSource(token);
  deadline.CancelAfter(TimeSpan.FromSeconds(5));
  foreach (Node node in graph.Nodes())
  {
    deadline.Token.ThrowIfCancellationRequested();
    Metric metric = await dashboard.FetchAsync(node.ID, deadline.Token);
    node.SetFloat("Metric.Complexity", metric.Value);
  }
}
  \end{lstlisting}

  \begin{itemize}
    \item \textbf{Link, do not replace.} \texttt{deadline.Token} is canceled
      by the caller \emph{or} by the timer, and carries both downwards; the
      \texttt{using} disposes that timer.
    \item \textbf{Tell the two apart.} In the \texttt{catch},
      \texttt{token.IsCancellationRequested} is false if the deadline fired
      --- a failure to report, unlike the other case.
  \end{itemize}
  \vspace{0.5ex}

  \hint{SEE wraps this whole pattern in \texttt{AsyncUtils.RunWithTimeoutAsync}.}
\end{solutionframe}

\begin{frame}[fragile]{\texttt{Task}: What the Rest of .NET Speaks}
  \framelabel{slide:task}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// A Task is a handle on work that is already running.
Task<string> download = client.GetStringAsync(url);  // starts here
string page = await download;                        // is waited for here

await Task.Delay(500, token);                        // UniTask.Delay(500)
string[] both = await Task.WhenAll(first, second);   // concurrently

// Task.Run is the one that really uses another thread:
Graph graph = await Task.Run(() => Parse(file));
  \end{lstlisting}
  \vspace{0.5ex}

  \begin{itemize}
    \item \textbf{You will read it more often than you write it.} File and
      network APIs, NUnit and most libraries return \texttt{Task}, and awaiting
      one is the same \texttt{await} you already know.
    \item \textbf{\texttt{Task.Run} is for computation}, not for making
      something asynchronous. It hands the delegate to the thread pool: real
      parallelism, and the only good reason to reach for it.
    \item \textbf{A \texttt{Task} is hot.} It is already running when you
      receive it, and a failure surfaces only at the \texttt{await}: if nobody
      awaits it, nobody learns that it failed.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{\texttt{Task} in Unity}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async Task ShowAsync(string url)
{
  string text = await client.GetStringAsync(url);
  label.text = text;             // fine: Unity's context brought us back
}

await LibraryCallAsync().ConfigureAwait(false);
transform.position = Vector3.zero;  // not fine: not the main thread now

await Task.Run(() => Parse(file));  // and never touch Unity in there
  \end{lstlisting}
  \vspace{0.5ex}

  \begin{itemize}
    \item Unity installs a synchronization context on the main thread, and
      \texttt{await} posts the continuation back to it. That alone makes
      \texttt{async Task} usable in a \texttt{MonoBehaviour}.
    \item \texttt{ConfigureAwait(false)} gives that up, and library code uses
      it freely. After awaiting somebody else's \texttt{Task} you cannot assume
      you are on the main thread.
    \item A \texttt{Task} knows nothing of play mode: it runs on after the user
      pressed stop, into objects that no longer exist. Pass
      \texttt{destroyCancellationToken} and check it.
  \end{itemize}
\end{frame}

\begin{frame}{UniTask: Why Not \texttt{Task}?}
  \texttt{Task} was designed for servers: thread pools, work stealing, many
  cores. A game has one main thread, a few milliseconds per frame, and must not
  allocate on every one of them.
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{UniTask} is a \texttt{struct}, and its state machines come
      from a pool, so awaiting allocates essentially nothing --- which matters
      when it happens in \texttt{Update}.
    \item It is driven by Unity's player loop directly, with no
      synchronization context in between, and lets you pick the timing
      (\texttt{PlayerLoopTiming.Update}, \texttt{LateUpdate}, \ldots).
    \item It knows Unity: you can await an \texttt{AsyncOperation}, a
      \texttt{UnityWebRequest}, or a coroutine.
  \end{itemize}
  \vspace{2ex}

  \hint{There is currently not a single \texttt{async Task} method
      in \texttt{Assets/SEE}: production code uses \texttt{UniTask} throughout.}
\end{frame}

\begin{frame}[fragile]{The UniTask Toolbox}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
await UniTask.Yield();                          // next frame
await UniTask.NextFrame();
await UniTask.Delay(500, cancellationToken: token);
await UniTask.WaitUntil(() => ready, cancellationToken: token);

await UniTask.WhenAll(taskA, taskB);            // both, concurrently
(a, b) = await UniTask.WhenAll(taskA, taskB);   // and their results

await UniTask.SwitchToThreadPool();             // leave the main thread
await UniTask.SwitchToMainThread();             // and come back

await UniTask.RunOnThreadPool(() => Parse(file), cancellationToken: token);
  \end{lstlisting}
  \vspace{1ex}

  \texttt{WhenAll} is the cheapest performance win in the list: two downloads
  awaited one after the other take the sum of their durations, awaited
  together they take the maximum.
\end{frame}

\begin{frame}[fragile]{Leaving and Returning to the Main Thread}
  \framelabel{slide:mainthread}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/DataModel/DG/IO/GXLParser.cs
try
{
  await UniTask.SwitchToThreadPool();      // parsing is pure CPU work
  while (await Reader.ReadAsync())
  {
    token.ThrowIfCancellationRequested();
    // ... build nodes and edges ...
  }
}
finally
{
  await UniTask.SwitchToMainThread();      // Unity API needs this thread
}
  \end{lstlisting}
  \vspace{1ex}

  Parsing a large GXL file is computation, not waiting, so \texttt{await}
  alone would not help: it would keep the main thread busy just the same. The
  parser therefore moves to a worker thread and must come back before anything
  touches Unity.
\end{frame}

\begin{exerciseframe}{Where Does This Run?}
  This throws;\\
  \texttt{UnityException: get\_name can only be called from the main thread}.\\
  Find the offending line and repair the method.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask<int> CountAsync(GameObject root, string file)
{
  await UniTask.SwitchToThreadPool();
  int lines = File.ReadAllLines(file).Length;
  Debug.Log($"{root.name}: {lines} lines\n");
  return lines;
}
  \end{lstlisting}
  \vspace{1ex}

  Which of the three statements after the switch are allowed on a worker
  thread?
\end{exerciseframe}

\begin{solutionframe}{Where Does This Run?}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask<int> CountAsync(GameObject root, string file)
{
  await UniTask.SwitchToThreadPool();
  int lines = File.ReadAllLines(file).Length;   // fine: pure .NET
  await UniTask.SwitchToMainThread();
  Debug.Log($"{root.name}: {lines} lines\n");     // needs the main thread
  return lines;
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{File.ReadAllLines} is ordinary .NET and belongs on the
      worker thread --- that is the point of the switch.
    \item \texttt{root.name} is Unity API, hence main thread only. It is the
      property access, not \texttt{Debug.Log}, that throws.
    \item Without the second switch the caller resumes on the worker thread
      too: UniTask continues on whichever thread completed the operation.
  \end{itemize}
  \vspace{1ex}

  \hint{Doing the switch in a \texttt{finally} block, as \texttt{GXLParser}
  does, is the safer habit: an exception must not leave the rest of the
  program on a worker thread.}
\end{solutionframe}

\begin{frame}[fragile]{Fire and Forget, on Purpose}
  \framelabel{slide:forget}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Controls/Actions/DeleteAction.cs
ShowDeletionNotificationAsync(message).Forget();

private static async UniTaskVoid ShowDeletionNotificationAsync(string text)
{
  ...
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{UniTaskVoid} is the honest \texttt{async void}: it cannot be
      awaited either, but it says so in the signature, and \texttt{Forget()}
      makes the decision visible at the call site.
    \item On a \texttt{UniTaskVoid} that is all \texttt{Forget()} does: it is
      an empty method, and the exception is routed by the state machine itself.
      On a \texttt{UniTask} it observes the result. Either way a failure
      reaches \texttt{UniTaskScheduler} and the console, while a cancellation
      is dropped in silence.
    \item Reach for it only where nobody could sensibly wait --- a
      notification, a fading highlight. Never for something whose result
      matters.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{From Coroutine to UniTask}
  \begin{center}
    \footnotesize
    \begin{tabular}{ll}
      \hline
      \textbf{Coroutine} & \textbf{UniTask}\\
      \hline
      \texttt{yield return null}              & \texttt{await UniTask.Yield()}\\
      \texttt{yield return new WaitForSeconds(t)} & \texttt{await UniTask.Delay(ms)}\\
      \texttt{yield return new WaitUntil(p)}   & \texttt{await UniTask.WaitUntil(p)}\\
      \texttt{yield return other}              & \texttt{await OtherAsync()}\\
      \texttt{yield break}                     & \texttt{return}\\
      \texttt{StartCoroutine(C())}             & \texttt{CAsync().Forget()}\\
      \hline
    \end{tabular}
  \end{center}
  \vspace{2ex}

  The rewrite is mechanical, and it buys three things a coroutine cannot
  offer: a return value, exceptions that reach the caller, and a
  \texttt{CancellationToken}. It also frees the code from needing a
  \texttt{MonoBehaviour} to live on.
\end{frame}

\begin{exerciseframe}{From Coroutine to UniTask}
  Rewrite this coroutine as an asynchronous method that can be canceled and
  reports whether the server answered.
  \vspace{1ex}

  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private bool succeeded;

private IEnumerator PollServer()
{
  for (int attempt = 0; attempt < 10; attempt++)
  {
    yield return new WaitForSeconds(1);
    if (Server.IsReachable())
    {
      succeeded = true;
      yield break;
    }
  }
  succeeded = false;
}
  \end{lstlisting}
\end{exerciseframe}

\begin{solutionframe}{From Coroutine to UniTask}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
private async UniTask<bool> PollServerAsync(CancellationToken token)
{
  for (int attempt = 0; attempt < 10; attempt++)
  {
    await UniTask.Delay(1000, cancellationToken: token);
    if (Server.IsReachable())
    {
      return true;
    }
  }
  return false;
}
  \end{lstlisting}
  \vspace{1ex}

  The \texttt{succeeded} field disappears: the answer is the return value, and
  the caller cannot read it too early any more. \texttt{yield break} becomes
  \texttt{return true}, and the loop needs no \texttt{MonoBehaviour}, so this
  is testable in edit mode.
  \vspace{1ex}

  \hint{\texttt{WaitForSeconds} measures scaled game time and pauses with the
  game; \texttt{UniTask.Delay} measures real time unless asked for
  \texttt{DelayType.DeltaTime}.}
\end{solutionframe}

\begin{frame}{Conventions in SEE}
  \begin{itemize}
    \item \texttt{UniTask} everywhere, \texttt{Task} nowhere (not yet). Production code
      contains no \texttt{async Task}; tests may use it because NUnit awaits
      it directly.
    \item Asynchronous methods end in \texttt{Async} and take
      \texttt{CancellationToken token = default} as their last parameter,
      passed on to everything they await.
    \item \texttt{async void} never; \texttt{UniTaskVoid} plus
      \texttt{Forget()} where fire-and-forget is really meant.
    \item Long computations go to the thread pool and return to the main
      thread in a \texttt{finally} block before touching Unity.
    \item New code uses coroutines only where something genuinely belongs to
      the player loop and no result is needed.
  \end{itemize}
  \vspace{2ex}

  \hint{If you are unsure whether to await or to forget, ask who would notice
  the failure. If nobody would, that is not a reason to forget --- it is a
  reason to await.}
\end{frame}
