\begin{frame}{A Scene Is Assembled, Not Constructed}
  In an ordinary C\# program you decide in code which objects exist. In Unity
  most of them exist because somebody placed them in a scene and saved it:
  \texttt{Assets/Scenes/SEEStart.unity} is such a file.
  \vspace{1ex}

  \begin{itemize}
    \item A \emph{GameObject} is an empty shell: a name, a \texttt{Transform}
      and nothing else. By itself it does nothing at all. It may have one parent
      and it may have children.
    \item A \emph{component} is what gives it data or behavior. A
      \texttt{Renderer} draws it, a \texttt{Collider} makes it solid, and a
      \texttt{MonoBehaviour} of your own runs code on it.
    \item A \emph{prefab} is a GameObject with its components and children
      saved as an asset, so that one scene can hold many instances of it and
      one edit can change them all.
  \end{itemize}
  \vspace{2ex}

  \hint{Nodes and edges of a dependency graph are represented as GameObjects in a code city.
      They are procedurally generated along with their necessary components.
      Their \texttt{NodeRef} or \texttt{EdgeRef} component, respectively,
      is used to refer to the underlying graph node/edge.}
\end{frame}

\subsection{Transform}

\begin{frame}[fragile]{Every GameObject Has a Transform}
  \framelabel{slide:transform}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
Transform t = gameObject.transform;  // always there, cannot be removed
GameObject back = t.gameObject;      // and back again

t.position = new Vector3(1.5f, 0, -3);   // x right, y up, z forward
t.rotation = Quaternion.Euler(0, 90, 0); // a quarter turn about y
t.localScale = new Vector3(2, 2, 2);     // twice as large in each axis

Vector3 angles = t.eulerAngles;      // the same rotation as three angles
t.Translate(0, 1, 0);                // one meter up
t.Rotate(0, 45, 0);                  // 45 degrees about the y axis
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item The \texttt{Transform} is the one component every GameObject has and
      none can do without. It holds three things and nothing else:
      \emph{position}, \emph{rotation} and \emph{scale}.
    \item Each of them is a triple over the axes $x$, $y$, $z$: $x$ to the
      right, $y$ up, $z$ away from the viewer --- a left-handed system.
    \item One unit is one meter. A cube of scale $1$ is a meter wide, and
      physics, gravity and the VR headset all take that literally.
    \item A rotation is stored as a \texttt{Quaternion}, not as three angles.
      \texttt{eulerAngles} converts for you, but reading it back need not give
      the numbers you wrote.
  \end{itemize}
\end{frame}


\subsection{Hierarchy}

\begin{frame}[fragile]{Parents and Children}
    \framelabel{slide:hierarchy}
    \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
Transform parent = t.parent;         // null for a root object
int children = t.childCount;
Transform first = t.GetChild(0);     // by index, in the order shown
foreach (Transform child in t)       // it enumerates its children
{
    Debug.Log($"{child.name}\n");
}

t.localPosition = new Vector3(0, 1, 0);  // local space, relative to parent
Vector3 world = t.position;              // world space, absolute
    \end{lstlisting}
    \vspace{1ex}

    \begin{itemize}
        \item The \texttt{Transform} carries the hierarchy as well as the pose.
        There is no separate scene tree: the editor's hierarchy window
        \emph{is} the \texttt{Transform} tree.
        \item A GameObject has at most one parent and any number of children, and
        a parent owns its subtree: destroying it destroys the children,
        deactivating it deactivates them.
        \item That is why the pose comes in two flavors. \texttt{localPosition}
        and \texttt{localRotation} are measured in the parent's space,
        \texttt{position} and \texttt{rotation} in the world's. Scale has no
        world counterpart you may set: \texttt{localScale} is the only one.
    \end{itemize}
\end{frame}

\begin{frame}[fragile]{Reparenting}
    \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
transform.SetParent(null);          // no parent anymore
transform.SetParent(parent);        // keeps the world pose, rewrites local
transform.SetParent(parent, false); // keeps the local values, moves it
    \end{lstlisting}
    \vspace{1ex}

    \begin{itemize}
        \item The \texttt{transform} of a \texttt{GameObject} holds the parent.
        \item A new parent cannot leave both coordinate spaces alone:
        \texttt{localPosition} lives in local space, \texttt{position} in world
        space, and the parent's scale and rotation are folded into everything
        below it. The second argument picks which of the two is kept.
    \end{itemize}
\end{frame}

\begin{exerciseframe}{Reparent Without Moving}
    \texttt{parent} sits at world position $(2, 0, 0)$ with scale $2$;
    \texttt{child} sits at $(6, 0, 0)$ with scale $1$ and has no parent yet.
    \vspace{1ex}

    \begin{enumerate}
        \item After \texttt{child.transform.SetParent(parent.transform)}: what are
        the child's \texttt{position}, \texttt{localPosition} and
        \texttt{localScale}?
        \item And after \texttt{SetParent(parent.transform, false)} instead?
    \end{enumerate}
\end{exerciseframe}

\begin{solutionframe}{Reparent Without Moving}
    \begin{enumerate}
        \item \texttt{position} stays $(6, 0, 0)$ --- that is the point of the
        one-argument form. To keep it, Unity rewrites the local values:
        \texttt{localPosition} becomes $(2, 0, 0)$, because the child is $4$
        world units past a parent scaled by $2$, and \texttt{localScale}
        becomes $0.5$, so that the world scale is still $1$.
        \item The local values are kept instead, so \texttt{localPosition} stays
        $(6, 0, 0)$ and the child jumps to $2 + 2 \cdot 6 = (14, 0, 0)$ at
        scale $2$. This is the form for UI and for freshly created children.
    \end{enumerate}
\end{solutionframe}

\subsection{Components}

\begin{frame}[fragile]{Getting at the Components}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/GameObjects/GameObjectExtensions.cs
Node node = gameNode.GetNode();  // executes GetComponent<NodeRef>().Value
Edge edge = gameEdge.GetEdge();  // both throw if the ref is missing

if (gameObject.TryGetComponent(out Renderer renderer))   // the safe form
{
    renderer.enabled = false;
}
// Assets/SEE/Game/Drawable/BlinkEffect.cs
Renderer[] all = obj.GetComponentsInChildren<Renderer>();  // whole subtree
BlinkEffect effect = obj.AddComponent<BlinkEffect>();      // at run time
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{GetComponent} looks at one GameObject only and yields
      \texttt{null} if nothing is there; \texttt{InChildren} and
      \texttt{InParent} walk the hierarchy.
    \item Unity overloads \texttt{==} for its \texttt{Object}: a destroyed
      object compares equal to \texttt{null} while the C\# reference still
      exists. \texttt{?.} and \texttt{??} do not know that and will happily
      call into a dead object.
    \item In SEE, never write \texttt{GetComponent<NodeRef>().Value}: use
      \texttt{GetNode}/\texttt{GetEdge}, or \texttt{TryGetNode}/%
      \texttt{TryGetEdge} when absence is normal.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{SEE Has Its Own, and They Are the Ones to Use}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/GameObjects/GameObjectExtensions.cs -- all three are extensions
// of GameObject, so they read like methods of it

Renderer r = obj.MustGetComponent<Renderer>();  // throws, naming obj and T
BlinkEffect b = obj.AddOrGetComponent<BlinkEffect>();  // adds it if absent

if (!obj.TryGetComponentOrLog(out Interactable interactable))  // logs an
{                                                              // error
    return;                                                    // for you
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item Each of the three replaces a pattern you would otherwise write by
      hand, and each says what should happen when the component is missing:
      throw, create it, or report and carry on.
    \item Use them. They are the house style and their messages name the game
      object and the component type, which a bare
      \texttt{NullReferenceException} does not.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{The \texttt{MonoBehaviour} Lifecycle}
    \framelabel{slide:lifecycle}
    \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
Awake()        // once, as the object comes into existence
OnEnable()     // every time it becomes enabled
Start()        // once, before the first Update, only if enabled
Update()       // once per frame -- Time.deltaTime is how long the last took
LateUpdate()   // after every Update; cameras follow here
FixedUpdate()  // per physics step: zero, one or many times per frame
OnDisable()    // becomes disabled, or is about to be destroyed
OnDestroy()    // once, at the very end
    \end{lstlisting}
    \vspace{1ex}

    \begin{itemize}
        \item Every \texttt{Awake} in the scene runs before any \texttt{Start} ---
        find yourself in \texttt{Awake}, reach for others in \texttt{Start}.
        \item \texttt{Awake} runs even for a disabled component; an inactive
        GameObject postpones it.
        \item Never write a constructor: Unity creates components, and a
        constructor cannot touch the scene.
        \item Every one of these must return before the frame can end. Longer work
        has to be spread over frames: coroutines and \texttt{UniTask}, in the
        lecture on asynchronous computing.
        \item Full details at
        {\tiny \url{https://docs.unity3d.com/6000.5/Documentation/Manual/execution-order.html}}.
    \end{itemize}
\end{frame}

\begin{exerciseframe}{Predict the Order}
    Two GameObjects, \texttt{A} and \texttt{B}, each carry a component that logs
    every one of \texttt{Awake}, \texttt{OnEnable}, \texttt{Start} and the first
    \texttt{Update}. The component on \texttt{A} holds a reference to \texttt{B}.
    \vspace{1ex}

    \begin{enumerate}
        \item Both are active when the scene loads. Which of the eight messages
        have a guaranteed order, and which do not?
        \item \texttt{B} is inactive when the scene loads, and \texttt{A} calls
        \texttt{b.SetActive(true)} in its \texttt{Start}. Now what is the order?
        \item \texttt{A} wants to read a value that \texttt{B} computes for
        itself. In which method does each of the two belong?
    \end{enumerate}
    \vspace{1ex}

    \hint{The lifecycle is on \slideref{slide:lifecycle}.}
\end{exerciseframe}

\begin{solutionframe}{Predict the Order}
    \begin{enumerate}
        \item \texttt{A.Awake} and \texttt{B.Awake} both precede
        \texttt{A.Start} and \texttt{B.Start}, which both precede either
        \texttt{Update}. Between \texttt{A} and \texttt{B} nothing is
        guaranteed: script execution order is arbitrary unless you configure it,
        and code that depends on it breaks when a scene is rebuilt.
        \item \texttt{A.Awake}, \texttt{A.OnEnable}, \texttt{A.Start}, then
        \texttt{B.Awake} and \texttt{B.OnEnable} inside the
        \texttt{SetActive} call, then \texttt{B.Start} --- still in the same
        frame, before any \texttt{Update}.
        \item \texttt{B} computes it in \texttt{Awake}, \texttt{A} reads it in
        \texttt{Start}. That pair is ordered by the engine, so it holds however
        the two objects happen to be visited.
    \end{enumerate}
\end{solutionframe}

\subsection{Prefabs}

\begin{frame}{Prefabs, Instances, Variants}
    \begin{itemize}
        \item The \emph{asset} is the original. An \emph{instance} in a scene
        keeps a link to it, so a change to the asset reaches every instance.
        \item An instance may deviate: any value you edit on it becomes an
        \emph{override}, shown in bold in the inspector, and an override is
        immune to later changes of that same value in the asset. \emph{Apply}
        pushes it back into the asset, \emph{Revert} throws it away.
        \item A \emph{variant} is a prefab whose base is another prefab. It is the
        override idea made permanent and reusable: the variant records what
        differs, everything else keeps following the base --- including
        components added to the base afterwards.
    \end{itemize}
    \vspace{2ex}

    \hint{Copying a prefab and editing the copy looks easier and costs you the
        link. The base can then be fixed a hundred times without the copy ever
        noticing. SEE uses prefab variants for its player avatars.}
\end{frame}

\begin{exerciseframe}{A Node Prefab}
  Create a new empty scene and build a miniature of what SEE draws:
  \vspace{1ex}

  \begin{enumerate}
    \item A cube named \texttt{Node}, carrying a component
      \texttt{NodeMarker} of your own with a label that you can type in the
      inspector without making the field public.
    \item Save the cube as a prefab and place three instances in the scene,
      each with a different label, one of them tinted red.
    \item \texttt{NodeMarker} logs its label once at start-up method \texttt{void Start()},
    and clicking the message in the console selects the object it came from.
  \end{enumerate}
  \vspace{1ex}

  Then change the scale of the cube in the prefab asset. Which of your three
  instances follow, and which do not? Why?
\end{exerciseframe}

\begin{solutionframe}{A Node Prefab}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
public class NodeMarker : MonoBehaviour
{
    [SerializeField] private string label = "unnamed";   // visible, private

    private void Start() // will be called by Unity; should be private
    {
        bool drawn = TryGetComponent(out Renderer _);
        Debug.Log($"{name}: label={label}, drawn={drawn}\n", this);
    }
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{[SerializeField]} is what makes a private field appear in
      the inspector and be saved with the scene. Making it public would do
      the same, and would also let every other class write it.
    \item The second argument of \texttt{Debug.Log} is the \emph{context}
      object: the console highlights it when you click the message.
    \item All three instances grow, except where you overrode the value.
      Tinting one red overrides its material only; scale was never overridden,
      so it still comes from the asset.
  \end{itemize}
\end{solutionframe}

\begin{exerciseframe}{Variant or Copy?}
  The player avatars live in \texttt{Resources/Prefabs/Players/CC4}: over a
  dozen characters --- \texttt{Caleb}, \texttt{Hanna}, \texttt{Karl} and the
  rest --- over one \texttt{BaseAvatar}.
  \vspace{1ex}

  \begin{enumerate}
    \item Make a variant of \texttt{BaseAvatar} of your own and give it another
      material. Then add a component to \texttt{BaseAvatar}. What does your
      variant do, and what would a duplicated copy have done?
    \item One of them is \emph{not} a variant. How do you find out which one,
      without opening every prefab in the inspector?
    \item Suppose the avatars all sit too low, and you raise the root position
      of \texttt{BaseAvatar} to fix them in one place. Open any variant's
      \texttt{.prefab} file in a text editor first, and predict whether your
      fix will arrive.
  \end{enumerate}
\end{exerciseframe}

\begin{solutionframe}{Variant or Copy?}
  \begin{enumerate}
    \item The variant picks the new component up by itself and keeps your
      material, because an override wins over the base only for the one value
      it overrides. A duplicated copy would keep the material too --- and
      never hear about the component.
    \item A variant's \texttt{.prefab} file begins with a
      \texttt{PrefabInstance} whose \texttt{m\_SourcePrefab} is the GUID of its
      base, a plain prefab does not. Searching the folder for the GUID in
      \texttt{BaseAvatar.prefab.meta} settles it in one step:
      \texttt{Assistant.prefab} is the only file without it.
    \item It will not arrive. Every one of the files already overrides the root
      \texttt{m\_LocalPosition} --- all of them to $(0, 0, 0)$ --- and an
      override is immune to a change of that same value in the base. A variant
      always records its own root transform, so this is the one property you
      can never fix centrally. The height has to go into each variant, below
      the root, or into the code that places the avatar.
  \end{enumerate}
\end{solutionframe}

\subsection{ScriptableObjects}

\begin{frame}[fragile]{Data That Is Not in the Scene}
  \framelabel{slide:scriptableobject}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
[CreateAssetMenu(fileName = "CityTheme", menuName = "SEE/City Theme")]
public class CityTheme : ScriptableObject   // no GameObject, no Transform
{
    public Color LeafColor = Color.white;
    public float MinBlockHeight = 0.01f;
}
...
CityTheme theme = Resources.Load<CityTheme>("Themes/Default");
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item A \texttt{ScriptableObject} is a serialized C\# object that lives as
      an asset instead of on a GameObject. Every \texttt{.asset} file in the
      project is an instance of one.
    \item You reference it, you do not copy it: everybody who points at the
      asset shares the one instance, so one edit reaches all of them --- and an
      edit made while the game is running survives leaving play mode.
    \item SEE declares none of its own, but depends on many: the URP
      pipeline assets (\texttt{Fastest}, \texttt{Beautiful}, \texttt{Fantastic}),
      \texttt{DefaultVolumeProfile}, \texttt{BeautifyProfile},
      \texttt{TMP Settings}, and \texttt{SEENetworkPrefabs.asset}, which is
      Netcode's prefab list.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{How SEE Configures Instead}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/EdgeSelectionAttributes.cs, cut to two settings
[Serializable]
public class EdgeSelectionAttributes : VisualAttributes
{
    public float Radius = 0.005f;
    public bool AreSelectable = true;

    private const string radiusLabel = "Radius";
    private const string areSelectableLabel = "AreSelectable";

    public override void Save(ConfigWriter writer, string label)
    {
        writer.BeginGroup(label);
        writer.Save(Radius, radiusLabel);
        writer.Save(AreSelectable, areSelectableLabel);
        writer.EndGroup();
    }
    // Restore on the next slide
}
  \end{lstlisting}
  \vspace{0.5ex}

  Every field needs three things: the field itself, a \texttt{const} label that
  names it in the file, and a \texttt{writer.Save} call that pairs the two.
\end{frame}

\begin{frame}[fragile]{\ldots{} and Reads Them Back}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// the same class, continued: Restore is the mirror image of Save
public override void Restore(Dictionary<string, object> attributes,
                             string label)
{
    if (attributes.TryGetValue(label, out object group)
        && group is Dictionary<string, object> values)
    {
        ConfigIO.Restore(values, radiusLabel, ref Radius);
        ConfigIO.Restore(values, areSelectableLabel, ref AreSelectable);
    }
}
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{ConfigIO.Restore} assigns the field only when the label is
      there, so an older file that does not mention a setting leaves its
      default alone. That is what keeps the format readable across versions.
    \item The two methods have to agree, label by label, and nothing checks
      that they do. A \texttt{writer.Save} without its
      \texttt{ConfigIO.Restore} writes a setting that is never read back ---
      silently, and only in the next session.
  \end{itemize}
\end{frame}

\begin{frame}{Why Not a \texttt{ScriptableObject}, Then?}
  \begin{itemize}
    \item The settings are plain \texttt{[Serializable]} classes, held as
      fields of the city component and written through a \texttt{ConfigWriter}
      into a text file --- \texttt{StreamingAssets/UserSettings.cfg} holds
      lines like \texttt{PlayerName : "Me";}
    \item A \texttt{.cfg} is human-editable and diffs line by line in git,
      while a \texttt{.asset} is Unity's own format --- and nobody can
      configure a headless run by editing one.
    \item The price is the code on the previous slide, once per settings class
      and then once per field: a label, a \texttt{writer.Save} call and a
      \texttt{ConfigIO.Restore} call, times twenty-odd settings classes.
      Forget one and that setting silently stops being saved, which is why
      there should be a test for every one of them.
  \end{itemize}
\end{frame}

\begin{exerciseframe}{Two Ways to Store a Setting}
  A city needs three settings: the color of leaf nodes, a minimal block
  height, and whether edges are animated. Build them twice.
  \vspace{1ex}

  \begin{enumerate}
    \item As a \texttt{ScriptableObject}: the class, one asset created from the
      menu, and a \texttt{MonoBehaviour} that reads the asset and logs the
      three values. Then change a value while the game runs --- what do you
      find after you leave play mode?
    \item In SEE's own style: a \texttt{[Serializable]} class deriving from
      \texttt{VisualAttributes} with \texttt{Save} and \texttt{Restore}. Write
      it out and read it back.
  \end{enumerate}
  \vspace{1ex}

  Which of the two would you rather review in a pull request, and which would
  you rather hand to somebody who starts SEE from the command line?
\end{exerciseframe}

\begin{solutionframe}{Two Ways to Store a Setting}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
[CreateAssetMenu(fileName = "CityTheme", menuName = "SEE/City Theme")]
public class CityTheme : ScriptableObject
{
    public Color LeafColor = Color.white;
    public float MinBlockHeight = 0.01f;
    public bool AnimateEdges;
}

public class ThemeUser : MonoBehaviour
{
    [SerializeField] private CityTheme theme;   // dragged in, or Resources
    private void Start() => Debug.Log($"{theme.LeafColor}\n", this);
}
  \end{lstlisting}
  \vspace{1ex}

  The value you changed in play mode is still changed afterwards. An asset is
  not a copy per run, and the editor writes it back to disk --- the classic
  way to lose a setting without noticing.
\end{solutionframe}

\begin{solutionframe}{Two Ways to Store a Setting}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
[Serializable]
public class ThemeAttributes : VisualAttributes
{
    public Color LeafColor = Color.white;      // and the other two
    private const string leafColorLabel = "LeafColor";

    public override void Save(ConfigWriter writer, string label)
    {
        writer.BeginGroup(label);
        writer.Save(LeafColor, leafColorLabel);
        writer.EndGroup();
    }
    // Restore reads attributes[label] back into the fields
}
  \end{lstlisting}
  \vspace{0.5ex}

  The \texttt{.cfg} wins the review --- a diff shows which setting moved and to
  what. It also wins the command line, because it can be edited without Unity.
  What it costs is the hand-written \texttt{Save} and \texttt{Restore} for
  every field, and that is exactly what a \texttt{ScriptableObject} would have
  given you for free.
\end{solutionframe}
