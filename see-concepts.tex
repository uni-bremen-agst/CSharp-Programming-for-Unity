\begin{frame}{A Graph, Shown as a City}
  Everything SEE displays is a graph. The data model underneath is a directed,
  attributed graph whose nodes also form a hierarchy: nodes stand for the
  artifacts of a software system, edges for the relations between them, and
  attributes for everything else known about either.
  \vspace{1ex}

  A \emph{code city} is one way of looking at that graph:
  \begin{itemize}
    \item a node becomes a block, and the node hierarchy becomes the nesting of
      blocks within blocks,
    \item an edge becomes an arc drawn from one block to another,
    \item a metric becomes a visual dimension, such as height, width or color.
  \end{itemize}
  \vspace{1ex}

  The graph is the model and exists without Unity; the city is a rendering of
  it. This lecture therefore begins with the graph and turns to the city
  afterwards.
\end{frame}

\subsection{The Graph}

\begin{frame}[fragile]{What a Graph Is Made Of}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/Core/
// Type inheritance hierarchy:
Attributable          // attributes, and notification when they change
  Graph               // the graph as a whole
  GraphElement        // everything in it that carries attributes
    Node
    Edge

// four kinds of attribute, on Graph, Node and Edge alike
node.SetToggle(name);
node.SetString(name, value);
node.SetInt(name, value);
node.SetFloat("Metric.Lines.LOC", 120);
node.TryGetFloat("Metric.Lines.LOC", out float loc);
  \end{lstlisting}
  \vspace{1ex}

  Nodes and edges carry no fields of their own beyond the structural ones.
  Everything a node knows about the artifact it stands for is an attribute of
  one of four kinds, looked up by name, which is why a new analysis can add
  data without a single change to the model.
\end{frame}

\begin{frame}[fragile]{Two Structures Over the Same Nodes}
  \framelabel{slide:twostructures}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/Core/Node.cs -- a tree
public Node Parent { ... }
public IList<Node> Children()
public int Level

// the very same class -- a directed graph
public ISet<Edge> Outgoings { get; private set; }
public ISet<Edge> Incomings { get; private set; }

// Assets/SEE/Graphs/Core/Edge.cs -- directed, hence source and target
public Node Source { get; set; }
public Node Target { get; set; }
  \end{lstlisting}
  \vspace{1ex}

  A node sits in a tree and in a graph at once, and the two are independent.
  The city renders the tree as nesting --- a method inside a class inside a namespace
  --- and the edges as the arcs between the blocks.
\end{frame}

\subsection{Node and Edge Types}

\begin{frame}[fragile]{Types Are Just Strings}
  \framelabel{slide:types}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/Core/GraphElement.cs
public string Type { ... }      // every node and every edge has one

// Assets/SEE/Graphs/Core/Graph.cs -- read off the data, not declared
internal HashSet<string> AllNodeTypes()
    => Nodes().Select(n => n.Type).ToHashSet();
internal HashSet<string> AllEdgeTypes()
    => Edges().Select(e => e.Type).ToHashSet();
  \end{lstlisting}
  \vspace{1ex}

  Every node and edge has a type.
  \vspace{1ex}

  A type is a string that arrived with the input, and SEE prescribes no
  vocabulary for it. \texttt{Class} and \texttt{Calls} are what an analysis of
  a program happens to emit; a graph of database tables could just as well use
  \texttt{Table} and \texttt{Foreign\_Key}, and nothing in the model would
  notice. Which types occur is therefore a question to the graph, not to SEE.
  \vspace{1ex}

  Almost: a few places do name a type, among them \texttt{File},
  \texttt{Directory} and \texttt{Clone}. They are few enough to count, and they
  are in most cases generated by SEE's own analyses.
\end{frame}

\begin{frame}[fragile]{The User Says What the Types Mean}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/AbstractSEECity.cs -- settings, not laws
[OdinSerialize, Tooltip("Edge types of hierarchical edges.")]
public HashSet<string> HierarchicalEdges = HierarchicalEdgeTypes();
public static HashSet<string> HierarchicalEdgeTypes() => new()
{ "Enclosing", "Belongs_To", "Part_Of", "Defined_In" };

[OdinSerialize, Tooltip("Visual attributes of nodes.")]
public NodeTypeVisualsMap NodeTypes = new();
  \end{lstlisting}
  \vspace{1ex}

  Both are city settings, editable in the inspector and at runtime.
  \begin{itemize}
    \item \texttt{HierarchicalEdges} names the edge types that mean
      containment: the nodes that nest are those connected by an edge of such a
      type. The four defaults are what SEE's usual inputs happen to emit.
    \item \texttt{NodeTypes} maps a node type to its visual attributes, among
      them whether such nodes are relevant at all. Keyed by the types found in
      the graph (\slideref{slide:types}), it fills itself once one is loaded.
  \end{itemize}
\end{frame}

\subsection{GXL Files}

\begin{frame}[fragile]{GXL In, GXL Out}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/IO/GXL/GraphWriter.cs
public static void Save(string filename, Graph graph,
                        string hierarchicalEdgeType)

// Assets/StreamingAssets/SEE/CodeFacts.gxl.xz
  \end{lstlisting}
  \vspace{1ex}

  GXL is the \emph{Graph eXchange Language}, an XML-based format for handing
  graphs from one tool to the next. It comes out of the software engineering,
  graph drawing and graph grammar communities, and it is what SEE both reads
  and writes. Its syntax is not worth your time: the wiki describes the dialect
  SEE accepts, the one defined by the Axivion
  Suite.\footnote{\url{https://github.com/uni-bremen-agst/SEE/wiki/GXL}}
  \vspace{1ex}

  The graphs shipped with SEE are compressed, which the reader handles by the
  file name extension, so a city loads a \texttt{.gxl.xz} without anyone
  unpacking anything.
\end{frame}

\begin{frame}[fragile]{The Tree Is Not in the File}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/IO/GXL/GraphReader.cs
public static async UniTask<Graph> LoadAsync(DataPath path,
    HashSet<string> hierarchicalEdgeTypes, string basePath, ...)
  \end{lstlisting}
  \vspace{1ex}

  GXL knows nodes and directed edges, and nothing else. The tree of
  \slideref{slide:twostructures} is nowhere in the file: the reader is handed
  the hierarchical edge types and builds the parent-child relation from the
  edges of those types. Read the same file with a different set and a different
  tree comes out.
  \vspace{1ex}

  Hence the asymmetry between the two ends: \texttt{LoadAsync} accepts a set of
  such types, \texttt{Save} emits one. A graph whose containment came from
  several types does not survive a round trip unchanged.
\end{frame}

\subsection{Attributes}

\begin{frame}[fragile]{Metrics Are Attributes}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/Core/StandardNames.cs
public const string Prefix = "Metric.";
public const string Lines  = Prefix + "Lines.";
public const string LOC    = Lines + "LOC";
public const string McCabe = Prefix + "McCabe_Complexity";

// Assets/SEE/Graphs/IO/CSV/MetricImporter.cs
public static async UniTask<int> LoadCsvAsync(Graph graph, DataPath path,
    char separator = ';', ...)
  \end{lstlisting}
  \vspace{1ex}

  A metric is a float attribute whose name begins with \texttt{Metric.}, and
  that convention is the whole mechanism: the CSV importer matches rows to
  nodes by ID and sets such attributes, the Axivion and JaCoCo importers add
  theirs under their own prefixes, and a city then maps a metric name to a
  visual dimension such as height or color.
\end{frame}

\begin{frame}[fragile]{Where the Code Is}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Graphs/Core/GraphElement.cs -- nodes and edges alike
public string Directory { ... }     // "Source.Path"
public string Filename  { ... }     // "Source.File"
public string Path()                // the two of them combined
public int? SourceLine   { ... }    // "Source.Line"
public int? SourceColumn { ... }    // "Source.Column"
public Range SourceRange { ... }

// Assets/SEE/Graphs/Core/Node.cs
public string SourceName { ... }
  \end{lstlisting}
  \vspace{1ex}

  These, too, are nothing but attributes, set by whichever analysis read the
  source code. They are what lets SEE open the right file at the right line:
  \texttt{ShowCodeAction} asks the graph element where it came from, and the
  code viewer follows.
\end{frame}

\subsection{Separation from Unity}

\begin{frame}[fragile]{The Graph Knows Nothing of Unity}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Utils/GraphElementExtensions.cs
public static bool HasGameObject(this GraphElement element)
    => GraphElementIDMap.Has(element.ID);

public static GameObject GameObject(this GraphElement element,
                                    bool mustFind = false)
  \end{lstlisting}
  \vspace{1ex}

  No class in \texttt{Graphs} derives from \texttt{MonoBehaviour} or
  touches a \texttt{GameObject}. The model is plain C\#, which is why the tests
  can load a real graph and check it without ever entering play mode.
  \vspace{1ex}

  The single bridge to the scene is the ID: a map from element ID to game
  object, asked for through these two extension methods. Everything the city
  does starts by crossing that bridge.
\end{frame}

\subsection{Code Cities}

\begin{frame}[fragile]{A Code City}
    \framelabel{slide:city}
    \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/AbstractSEECity.cs
public abstract partial class AbstractSEECity : SerializedMonoBehaviour
{
    public abstract Graph LoadedGraph { get; protected set; }
    public abstract IGraphRenderer Renderer { get; }
    public NodeTypeVisualsMap NodeTypes = new();
    ...
 }
    \end{lstlisting}
    \vspace{1ex}

    \begin{itemize}
        \item A \textit{code city} is a \texttt{GameObject} holding an
        instance of a subclass of \texttt{AbstractSEECity}.
        \item An \texttt{AbstractSEECity} has the settings to generate
        all \texttt{GameObject}s for a code city (loading and rendering a \texttt{Graph}).
        \item A \textit{game node} is a \texttt{GameObject} representing
        a graph \texttt{Node} in a code city.
        \item A \textit{game edge} is a \texttt{GameObject} representing
        a graph \texttt{Edge} in a code city.
    \end{itemize}
\end{frame}

\begin{frame}{\texttt{GameObject} Hierarchy of a Code City}
  \begin{columns}[c]
    \begin{column}{0.46\textwidth}
      \begin{itemize}
        \item There is at most one root game node that is an immediate child
        of a code city.
        \item The game-node hierarchy and graph-node hierarchy
        are isomorphic.
        \item All game edges are immediate children of the code city.
      \end{itemize}
    \end{column}
    \begin{column}{0.5\textwidth}
      %%% \incgraphics adds a \colorbox, whose \fboxsep would otherwise
      %%% push the image past the column edge.
      \incgraphics{width=\dimexpr\textwidth-2\fboxsep\relax}%
                  {figures/CloneCityHierarchy.png}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}[fragile]{Scene Constraints}
    \begin{itemize}
        \item  A scene may hold several cities side by side,
        each with its own data and settings.
        \item The \texttt{name} of a game node/edge equals the \texttt{ID}
        of a graph \texttt{Node}/\texttt{Edge}.
        \item The \texttt{name} of a game node/edge is unique within
        a scene at a particular point in time.
    \end{itemize}
    \vspace{1ex}

    \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// game object -> graph element: read the NodeRef/EdgeRef component
gameObject.TryGetNode(out Node node);    // false if there is none
gameObject.TryGetEdge(out Edge edge);
Node n = gameObject.GetNode();           // throws if there is none

// graph element -> game object: by ID, which is the game object's name
GameObject gameNode = GraphElementIDMap.Find(node.ID);
GameObject gameEdge = GraphElementIDMap.Find(edge.ID);
    \end{lstlisting}
    \vspace{1ex}

    \hint{The way back leads through the \texttt{ID} only, and that is no
    accident: a net action (\slideref{slide:netaction}) cannot send a
    reference, but it can send an \texttt{ID}.}
\end{frame}

\begin{frame}[fragile]{The Family of Cities}

AbstractSEECity                  the component, the settings, the node types

 +-- SEECity                     one graph

\subsection{Declaring Settings}

\begin{frame}[fragile]{Settings Are Annotated, Not Coded}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/SEECity.cs
[OdinSerialize, ShowInInspector,
 Tooltip("A graph provider yielding the data ..."),
 TabGroup(DataFoldoutGroup), RuntimeTab(DataFoldoutGroup), ...]
public SingleGraphPipelineProvider DataProvider = new();
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{TabGroup} places the field in the editor inspector,
      \texttt{RuntimeTab} in the configuration menu that SEE builds at run
      time by reflecting over these very fields.
    \item The same fields are written to and read from the city's
      configuration file by \texttt{ConfigWriter} and \texttt{ConfigReader}.
    \item One annotated field therefore yields three things at once: an
      inspector row, a menu entry, and a line in the configuration file. Adding
      a setting means adding a field, not writing user interface code.
  \end{itemize}
\end{frame}

\subsection{Configuring a City}

\begin{frame}[fragile]{A User Decides how a City is Rendered}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/NodeLayoutKind.cs
EvoStreets, Balloon, RectanglePacking, Treemap, CirclePacking,
Reflexion, IncrementalTreeMap, FromFile

// Assets/SEE/Game/City/EdgeLayoutKind.cs
None, Straight, Spline, Bundling

// Assets/SEE/Game/City/AbstractSEECity.cs
public NodeLayoutAttributes NodeLayoutSettings = new();
public EdgeLayoutAttributes EdgeLayoutSettings = new();
public NodeTypeVisualsMap NodeTypes = new();
  \end{lstlisting}
  \vspace{1ex}

  Where the blocks go, how the arcs between them are drawn, and what a single
  block looks like are three independent settings. The first two are one choice
  each out of a fixed set of algorithms. The third is a choice per node type,
  and hence the only one that grows with the graph.
\end{frame}

\begin{frame}[fragile]{A Metric per Dimension}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/VisualNodeAttributes.cs -- per node type
public bool IsRelevant = true;
public NodeShapes Shape = NodeShapes.Blocks;  // or Cylinders, Bars, ...
public string WidthMetric  { ... }            // MetricToLength[0]
public string HeightMetric { ... }            // MetricToLength[1]
public string DepthMetric  { ... }            // MetricToLength[2]
public ColorProperty ColorProperty = new();
public bool ShowNames = false;
  \end{lstlisting}
  \vspace{1ex}

  The three edge lengths of a block are not numbers but metric \emph{names}.
  The renderer looks that attribute up on every node and scales the block
  between \texttt{MinimalBlockLength} and \texttt{MaximalBlockLength}. Put a
  different name there and the city means something else, with no line of code
  touched.
  \vspace{1ex}

  Color works the same way: \texttt{ColorProperty} either paints by node type,
  optionally shaded by nesting level, or maps a metric onto a color range.
\end{frame}

\begin{frame}{And the Other Dials}
  Beyond the layouts and the blocks, a city carries one settings object per
  concern, each annotated as on the previous slides and therefore present in
  the inspector, in the runtime menu and in the configuration file:
  \begin{itemize}
    \item \texttt{LabelSettings} and \texttt{TooltipSettings} for what is
      written next to a node and what appears when it is hovered,
    \item \texttt{ErosionSettings} for the erosion icons above a node and
      \texttt{MarkerAttributes} for how added or changed nodes are marked,
    \item \texttt{MetricToColor} for the color ranges metrics are mapped onto,
      \texttt{HiddenEdges} and \texttt{EdgeSelectionSettings} for which edges
      are drawn at all and what selecting one does.
  \end{itemize}
  \vspace{1ex}

  None of this is worth memorizing. What is worth knowing is that the answer to
  \emph{can the user change that} is almost always yes, and that the field
  named after the concern is where to look.
\end{frame}

\subsection{Graph Providers}

\begin{frame}[fragile]{Where the Graph Comes From}
  \framelabel{slide:provider}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/City/SEECity.cs
public SingleGraphPipelineProvider DataProvider = new();

public virtual async UniTask LoadDataAsync()
{
  ...
  LoadedGraph = await DataProvider.ProvideAsync(new Graph(""), this,
                                                ReportProgress, token);
  ...
}
  \end{lstlisting}
  \vspace{1ex}

  The city itself reads no file and calls no tool. It hands an empty graph to
  its provider and takes back a finished one. Which files, which repository,
  which analysis --- none of that is the city's business.
\end{frame}

\begin{frame}[fragile]{A Graph Provider Transforms a Graph}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
public abstract UniTask<T> ProvideAsync(T graph, AbstractSEECity city,
                                        Action<float> changePercentage,
                                        CancellationToken token);

// GXLSingleGraphProvider: ignores the input, produces a graph
return await GraphReader.LoadAsync(Path, city.HierarchicalEdges, ...);

// CSVGraphProvider: takes the graph, adds metrics, returns it
await MetricImporter.LoadCsvAsync(graph, Path, token: token);
return graph;
  \end{lstlisting}
  \vspace{1ex}

  Graph in, graph out --- that one signature is what makes providers
  composable. A provider is not a loader but a step, and only the first step
  of a pipeline usually ignores what it was given.
\end{frame}

\begin{frame}{Sources, Augmenters, Combiners}
  \begin{center}
    \footnotesize
    \begin{tabular}{ll}
      \hline
      \textbf{Role} & \textbf{For example}\\
      \hline
      Produce a graph      & \texttt{GXLSingleGraphProvider},
                             \texttt{GitBranchesGraphProvider}\\
      Add to a graph       & \texttt{CSVGraphProvider},
                             \texttt{JaCoCoGraphProvider},\\

      \hline
    \end{tabular}

  \vspace{2ex}

  A typical pipeline reads a GXL file, then adds coverage from JaCoCo, then
  adds issues from a report. Each step is configured separately and none of
  them knows about the others.
  \vspace{1ex}

  \hint{The augmenters expect a graph and complain if they get none. Order in
  the pipeline is therefore not a matter of taste.}
\end{frame}

\begin{frame}[fragile]{One Graph or a Series}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]

public abstract class SingleGraphProvider
  : GraphProvider<Graph, SingleGraphProviderKind>

public abstract class MultiGraphProvider

// SEECity            LoadedGraph       = await ...(new Graph(""), ...)

\subsection{Multiple Players}

\begin{frame}{Why Several People in One Room}
  SEE addresses distributed development teams, and that is what the third
  dimension is for: the visualization and the people looking at it are in the
  same virtual room. A team member is not a cursor but an avatar one can turn
  to, point at something with and read the face of, so the communication is
  verbal and non-verbal at once.
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{Game/Avatars} drives an avatar's face and hands from a webcam
      or from a headset's lip and eye tracking, and synchronizes both, so
      mimics and gestures reach the others
      (\texttt{BlendshapeExpressionsNetAction},
      \texttt{AvatarHandAnimationsSync}).
    \item \texttt{Dissonance} carries the voice chat, with a text chat
      alongside it for whatever is easier typed than said.
    \item \texttt{Game/Drawable} adds whiteboards to draw on together, shared
      through the net actions of the next subsection
      (\texttt{Net/Actions/Drawable}).
  \end{itemize}
\end{frame}

      in the city the others have built by then.
    \item A host is a server and client on the same machine.
  \end{itemize}

\subsection{Net Actions}

\begin{frame}[fragile]{Every Change Happens Twice}
  \framelabel{slide:netaction}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Controls/ReversibleActions/DeleteAction.cs
// Actual deletion (on all clients and locally).
new DeleteNetAction(go.name, removeNodeTypes).Execute();
GameElementDeleter.Delete(go, removeNodeTypes);

// Assets/SEE/Net/Actions/GraphElement/DeleteNetAction.cs
public override void ExecuteOnClient()
{
  GameObject objToDelete = Find(GraphElementID);
  GameElementDeleter.Delete(objToDelete, RemoveNodeTypes);
}
  \end{lstlisting}
  \vspace{1ex}

  The change itself lives in neither class. Both the action and its network
  twin call the same helper in \texttt{SEE.SceneManipulation}, so what
  the other players see cannot drift from what you see. The local half is a
  full-blown action with a life cycle (\slideref{slide:action}); the remote
  half is one method.
\end{frame}

\begin{frame}[fragile]{The Life of a NetAction}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Net/Actions/AbstractNetAction.cs
public void Execute(ulong[] recipients = null)
{
  Network.BroadcastAction(ActionSerializer.Serialize(this), recipients);
}

public virtual void ExecuteOnServer() { }   // default: nothing
public abstract void ExecuteOnClient();     // every client but the sender
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item The action travels to the server as a string, and the server passes
      it on with \texttt{RpcTarget.Not(senderId)}: the sender has already made
      the change locally and must not make it twice.
    \item \texttt{Requester} carries the client identifier, so a receiver can
      tell whose action it is executing.
    \item Actions too large for one packet are cut into fragments and put back
      together on the far side.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{What May Travel}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Net/Actions/GraphElement/DeleteNetAction.cs
// Note: All attributes are made public so that they will be serialized
// for the network transfer.
public bool RemoveNodeTypes;

// and never a reference; the object is found again on each client:
GameObject objToDelete = Find(GraphElementID);
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item A net action is serialized with \texttt{JsonUtility}: every field
      that must travel is public and not \texttt{readonly}.
    \item A \texttt{GameObject} or a \texttt{Component} cannot travel, because
      the receiving client has different objects at different addresses. Send
      the identifier and look it up again.
    \item In the editor, \texttt{Execute} checks serializability before
      sending, so this mistake is caught while you are testing, not in a
      session with others.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{Late Joiners and Ephemera}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Net/Actions/AbstractNetAction.cs
public virtual bool ShouldBeSentToNewClient { get => true; }

// Assets/SEE/Net/Actions/SetHoverNetAction.cs and its kin
public override bool ShouldBeSentToNewClient { get => false; }
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item The server keeps every action that describes the world, and replays
      them to a client that joins later. That is how a newcomer arrives in a
      city somebody else built.
    \item Hovering, grabbing, highlighting, pointing, sounds: these describe a
      moment, not the world. They opt out, or a late joiner would inherit a
      history of somebody else's mouse.
    \item Deciding this correctly is part of writing a net action. Ask whether
      a player who arrives in an hour still needs to know.
  \end{itemize}
\end{frame}

\subsection{The Action History}

\begin{frame}[fragile]{An Action Has a Life Cycle}
  \framelabel{slide:action}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Controls/ReversibleActions/IReversibleAction.cs
void Awake();            // once, when the action is first started
void Start();            // whenever it is (re-)enabled
bool Update();           // every frame; true means completed
void Stop();             // another action takes over
void Undo();  void Redo();
IReversibleAction NewInstance();

enum Progress { NoEffect, InProgress, Completed }
  \end{lstlisting}
  \vspace{1ex}

  An action is a mode, not a method call: it is started, then asked every
  frame whether it is done. When \texttt{Update} finally returns true, the
  history records the action and immediately puts a fresh instance of the same
  kind in its place, so the tool stays selected.
\end{frame}

\begin{frame}[fragile]{Two Histories}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/ActionHistory/ActionHistory.cs
private Stack<IReversibleAction> UndoHistory { get; } = new();
private Stack<IReversibleAction> RedoHistory { get; } = new();

private readonly List<GlobalHistoryEntry> globalHistory = new();

public readonly struct GlobalHistoryEntry
{
  public bool IsOwner { get; }              // did I execute it?
  public HistoryType ActionType { get; }    // Action or UndoneAction
  public string ActionID { get; }
  public HashSet<string> ChangedObjects { get; }
}
  \end{lstlisting}
  \vspace{1ex}

  The two stacks are yours alone and hold the real objects. The global history
  is shared: every player has the same list, kept in step by
  \texttt{NetActionHistory} with \texttt{Push}, \texttt{Delete}, and
  \texttt{Replace}.
\end{frame}

\begin{frame}{Undoing in Company}
  \begin{itemize}
    \item Undo is not the last thing that happened but the last thing
      \emph{I} did. \texttt{IsOwner} in the global history is what makes that
      distinction possible, and \slideref{slide:netaction} is why the question
      arises at all.
    \item Before undoing, SEE looks at every entry recorded after yours. If
      somebody else has touched one of your \texttt{ChangedObjects} since,
      undoing would silently discard their work, and \texttt{UndoImpossible}
      is raised instead.
    \item An action that has had no effect yet is not undone but simply
      dropped: undoing it would give the user no visible answer to a key
      press.
  \end{itemize}
  \vspace{2ex}

  \hint{This is why \texttt{GetChangedObjects} is not optional paperwork. An
  action that under-reports what it changed makes conflicting undos possible;
  one that over-reports makes legitimate undos fail.}
\end{frame}

\subsection{Operators}

\begin{frame}[fragile]{One Owner per Game Element}
  \framelabel{slide:operator}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Extensions/GameNodeExtensions.cs -- adds it if absent
NodeOperator nodeOperator = gameNode.NodeOperator();
EdgeOperator edgeOperator = gameEdge.EdgeOperator();

// Assets/SEE/Game/Operator/NodeOperator.cs
nodeOperator.MoveTo(newPosition, factor: 1);
nodeOperator.ResizeTo(newLocalScale, newPosition);
nodeOperator.ChangeColorsTo(color);

// Assets/SEE/Game/Operator/EdgeOperator.cs
edgeOperator.MorphTo(newSpline);          // one spline into another
edgeOperator.ShowOrHide(show, animationKind);
  \end{lstlisting}
  \vspace{1ex}

  A layout animation, a drag, a hover, a reflexion change and an incoming net
  action may all want to change the same node in the same frame. Writing to
  \texttt{transform} directly, whichever runs last wins, and which that is
  depends on script execution order. The operator is the one component allowed
  to change the element, so the requests have somewhere to meet.
\end{frame}

\begin{frame}[fragile]{Conflicting Change Requests}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/Operator/AbstractOperator.cs -- the same property twice
if (EqualityComparer.Equals(target, TargetValue) && duration > 0)
{
  return new DummyOperationCallback<C>();  // already heading there
}

// ... and properties that cannot both animate
KillAnimator(complete);
foreach (IOperation operation in
         ConflictingOperations.Where(x => x.IsRunning))
{
  operation.KillAnimator(true);            // complete it, then override
}
  \end{lstlisting}
  \vspace{0.5ex}

  \begin{itemize}
    \item Asking again for the value an element is already moving towards does
      nothing, so repeated requests neither restart nor flicker. A different
      value redirects the motion from wherever the element is now.
    \item The \texttt{true} is the interesting part: a conflicting animation is
      not abandoned but jumped to its own target first, so the losing request
      still takes effect and merely stops animating.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{The Value It Is Supposed to Have}
  \begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
// Assets/SEE/Game/Operator/NodeOperator.cs, in UpdateEdgeLayout
ourTransform.position = new Vector3(positionX.TargetValue,
                                    positionY.TargetValue,
                                    positionZ.TargetValue);
ourTransform.localScale = scale.TargetValue;
// ... and only now recalculate the layout of every attached edge
  \end{lstlisting}
  \vspace{1ex}

  \begin{itemize}
    \item \texttt{TargetValue} is where the element is \emph{going}, which
      during an animation is not where it is. The edges are laid out against
      the node's destination while the node is still gliding there.
    \item Hence writing to \texttt{transform} behind the operator's back is
      worse than merely skipping an animation: it leaves \texttt{TargetValue}
      lying, and the \emph{next} edge layout is computed for a destination
      that was never reached.
    \item The remote half of a resize asks the very same operator
      (\slideref{slide:netaction}), so what the others see is animated by the
      same code that animates it here.
  \end{itemize}
\end{frame}
